# contextual-history — optional native helper module

> **TL;DR**: `make` (auto-fetches zsh source, configures, builds, produces `zsh/contextual_history.{so,bundle}`). Then either `make install` to put it on `$module_path`, or `zstyle ':contextual-history:*' use-module true` in your `.zshrc` (before sourcing the plugin) to use it from this directory.

This is an optional zsh module that provides a `contextual-history-tee` builtin used
by the contextual-history plugin's tee path. The plugin works fine
without it (falls back to a portable pure-shell implementation);
building and installing this module replaces the manual lock + printf
with native zsh primitives:

- `lockhistfile` / `unlockhistfile` from `Src/hist.c` — automatically
  matches zsh's choice of lock protocol (`HIST_FCNTL_LOCK` on → fcntl,
  default → `<file>.LOCK` symlink).
- `unmeta` for path metafication, matching zsh's internal conventions.

Net result: the tee writer interlocks with stock zsh's own
`SHARE_HISTORY` / `INC_APPEND_HISTORY` writers on the same file, even
across multi-syscall edge cases (huge pasted commands) that the
pure-shell fallback's lock-free atomicity can't cover.

## Building

```sh
make                  # auto-fetch zsh source matching $ZSH_VERSION, configure,
                      # build zsh, build zsh/contextual_history.{so,bundle}.  ~30s on first run.
make ZSH_SRC=/path    # use an existing zsh source tree (must be ./configure'd
                      # AND `make`-built, so generated headers exist)
```

The Makefile auto-detects your zsh version (via `zsh -c 'echo
$ZSH_VERSION'`), downloads the matching tarball from SourceForge into
`build/zsh-X.Y/`, runs `./configure` and `make` there to generate the
needed headers, then compiles `contextual_history.c` against those headers.

The first run takes ~30s (network fetch + zsh build). Subsequent runs
skip the fetch/configure/build of zsh — only the module recompile
(<1s) runs.

If you already have a configured-and-built zsh source tree somewhere,
point `ZSH_SRC` at it to skip the fetch step.

### Why does it need zsh's source / build?

`contextual_history.c` references zsh-internal functions (`lockhistfile`,
`unlockhistfile`, `unmeta`) and uses zsh's module ABI. We include
`zsh.h`, `zsh_system.h`, and `config.h` — these are committed in the
zsh source tarball except `config.h` which is generated by
`./configure`. A handful of other headers (`zshcurses.h`, `zshterm.h`,
`sigcount.h`, etc.) are generated by zsh's own `make` via awk/sed
scripts, so we run `make` in the source tree to produce them.

We deliberately skip including `zsh.mdh` (which would also pull in
~30 generated `.epro` prototype files) and instead `extern`-declare
the few zsh functions we use. That's why we don't need a fully-built
zsh's `.epro` files.

## Installing

```sh
make install                    # install into $module_path[1] (typically the
                                # homebrew/system zsh's module dir)
make install DEST=/some/path    # install elsewhere (must be on $module_path)
```

Or use it from the source tree without installing:

```zsh
# In .zshrc, BEFORE sourcing the plugin:
zstyle ':contextual-history:*' use-module true
source /path/to/contextual-history.zsh
```

(Equivalent env-var form: `CONTEXTUAL_HISTORY_USE_MODULE=true`.)

Setting `use-module` makes the plugin prepend `module/` to
`$module_path` so the locally-built `.so`/`.bundle` is discoverable.

## Verification

```sh
zsh -c 'zmodload zsh/contextual_history && echo OK'
zsh -c 'zmodload zsh/contextual_history; which contextual-history-tee'
```

Both should print successfully if the module is on a `$module_path`
directory.

## Cross-platform notes

- **macOS**: builds as `.bundle` via `cc -bundle -undefined
  dynamic_lookup`. Symbols from the running zsh resolve at load time.
- **Linux**: builds as `.so` via `cc -shared`. Same dynamic-link model.
- **Symbol naming**: the module's entry-point functions are defined
  twice — once as plain (`setup_`, `boot_`, etc.) and once with the
  zsh-namespace suffix (`plain symbols`, etc.). Stock macOS/Homebrew
  zsh uses `SHORTBOOTNAMES=yes` (looks up the plain names);
  some Linux source builds default to `SHORTBOOTNAMES=no` (looks up the
  suffixed names). Defining both makes the module portable across both.

## When NOT to bother

The pure-shell fallback is good enough for the vast majority of use
cases. Single-line `printf >> file` writes are kernel-atomic with
`O_APPEND`, and the pure-shell tee replicates zsh's `lockhistfile`
protocol so it interlocks with stock zsh writers on the same file.

The native module is meaningfully better only when:

- You routinely paste multi-kilobyte command lines (rare; could trigger
  multi-syscall writes that the lock-free fallback's per-write atomicity
  doesn't cover, where the native helper's held-lock does).
- You care about strict bytewise serialisation under all conditions.

If neither applies, skip the build. The plugin will use the pure-shell
path automatically.
